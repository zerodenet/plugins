# 共享插件市场提案

[English](marketplace-design.md) · **简体中文**

**状态：草案。** 本提案描述面向 ZBoard、ZNet Sink 和后续宿主的共享分发层。ZBoard 当前实现了自己的 v1 目录和 `.zbplugin` 格式，提议的 v2 格式尚未实现。

## 动机

用户应能在同一个入口发现 ZeroDeNet 插件。发布者需要统一描述版本、目标宿主、兼容性和制品；宿主需要足够的签名信息来选择并校验适用的包，同时掌握安装与执行过程。

共享目录可同时服务公共网站和产品内市场。宿主通常展示兼容插件，公共网站可以展示全部支持的宿主，并解释兼容要求。

## 范围

市场覆盖插件发现、发布者元数据、版本索引、签名目录和制品分发。插件运行时、业务 API、私有数据和生命周期事务由各宿主负责，具体见[架构说明](governance.zh-CN.md)。

所有插件源码均位于独立仓库。市场在 `main` 同时维护 `catalogs/zboard.json` 和 `catalogs/znet-sink.json`。[注册表格式](registry-format.zh-CN.md)定义源记录格式；签名运行时分发仍属于本文提案。接入市场需要提交元数据，无须迁入源码。

## 发行模型

提议的目录以稳定插件 ID 组织发行版本，为各目标宿主分别提供可安装制品。

| 元数据 | 用途 |
| --- | --- |
| 插件 ID、发布者、版本 | 稳定身份和版本归属 |
| 宿主 ID 与版本范围 | 目标应用和兼容版本 |
| 包格式与 API 版本 | 安装和运行时契约；适用时包含页面桥版本 |
| OS 与架构 | 支持的运行目标，或明确声明平台无关 |
| 能力与扩展贡献 | 所需宿主操作和提供的界面 |
| 制品地址、字节数、SHA-256 | 内容不可变的下载标识和完整性 |
| 签名与密钥标识 | 制品来源 |

一个制品对应一个宿主。同一宿主制品可以包含多个平台二进制和页面范围。即使属于同一插件条目，不同宿主的发行版本也可以独立演进。

签名的包清单或封装必须绑定目标宿主和兼容要求。安装器比对包与目录信息，离线导入执行相同检查。签名封装与 v2 JSON schema 的具体格式仍待设计。

## 信任模型

目录签名和包发布是不同角色，宿主分别按配置的信任进行校验。通过不可信目录获得的发布者公钥不能自行建立信任。

目录可以描述撤回和密钥轮换信息。宿主策略决定这些记录如何影响安装与已有实例，包括离线时的行为。市场响应不能授予能力或删除宿主业务数据。

## 兼容 ZBoard v1

ZBoard 当前解析器只接受 schema v1 字段，识别 `public`、`account` 和 `admin` 页面范围，并要求包声明 `requires.zboard`。将 v2 字段或客户端条目加入该目录会导致校验失败。

因此，发布层应同时提供共享 v2 目录和独立签名的兼容目录。相对路径示例为 `catalogs/zboard/v1/catalog.json`，这是建议布局，并非已发布端点。兼容文档只包含 ZBoard v1 条目和 `.zbplugin` 制品。

现有 ZBoard 安装可直接使用兼容目录，无需先升级 v2 解析器。下载位置需满足当前宿主的 HTTPS 直达要求。客户端在实现 v2 前使用自己的目录契约。

## 待定事项

- JSON schema、签名封装和宿主标识注册规则。
- 发布者接入、可信密钥轮换和撤回政策。
- 制品托管、可用性监控和目录续签。
- 跨宿主 API 版本及平台的版本选择。
- 由客户端项目负责的运行时能力和隔离要求。

## 接入与验证

先确定分发契约，再发布并验证兼容 ZBoard 的制品和目录。随后为 ZBoard 增加 v2 消费能力，并在 ZNet Sink 的插件生命周期和 API 实现后接入客户端。

验收应覆盖在线与离线路径的跨宿主拒绝、目录与包身份不一致、签名失败、多宿主与平台选择、v1 兼容，以及宿主升级失败恢复。每个实现应明确其支持的提案范围。
