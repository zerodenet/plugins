# Unified marketplace implementation plan

**English** · [简体中文](marketplace-implementation-plan.zh-CN.md)

Status: planned. Use Astro + Minted Directory Astro, with listing and detail layouts informed by Ever Works. Existing catalog contracts remain active until migration is complete.

## Scope

One marketplace entry point serves discovery and host-filtered queries. ZBoard and ZNet Sink explicitly send their host identity; do not infer it from IP, Referer or User-Agent. Register one product and trusted publisher repository, with host-specific release artifacts generated by publisher tooling.

Hosts retain installation, updates, signature verification, permissions and runtime management. The registry never builds or executes submitted plugins. Exclude comments, accounts, profiles, favorites, ratings, payments and an administration backend from the first release.

## Architecture

- Use [Minted Directory Astro](https://github.com/masterkram/minted-directory-astro), pin a verified upstream commit and retain MIT notices. Adapt the information hierarchy of [Ever Works](https://github.com/ever-works/directory-web-template); review licensing separately before copying its code.
- Serve static assets and a read-only /api/ query service under one domain, preferably using a Cloudflare Worker with static assets. No database is required. GitHub Actions builds and deploys. GitHub Pages is optional and would need separate routing for /api/.
- Maintain stable product registration and trusted release discovery information. Authors publish generated manifests containing versions, channels, commits, target hosts, package IDs, compatibility, artifacts, hashes and signatures.
- Generate a versioned marketplace snapshot with provenance and freshness metadata. It is derived data, not another manually maintained catalog. Website and hosts share it and identical query semantics.
- Keep GitHub credentials in build infrastructure. Runtime queries never fan out to publisher repositories. Keep catalog provenance separate from package trust; submitted keys are not automatically trusted.

## Query contract draft

GET /api/plugins accepts host, q, category, pagination and sorting. An omitted host supports website discovery. host=zboard returns only ZBoard targets; host=znet-sink returns only client targets. GET /api/plugins/:id accepts the same host scope and never substitutes another host's package.

Optional host_version, os, arch and channel further filter results; stable is the default channel. Missing compatibility inputs mean only host-level suitability has been established. Distinguish source-only listings from installable releases. Define invalid parameter errors, pagination, snapshot versioning and ETags; cache keys include every effective filter.

## Stages and acceptance

### P0: Baseline

Inventory existing uncommitted registry changes without overwriting them. Inspect published feeds and both consumers before assigning schema versions. Verify Minted's static build, JSON input, detail routes, search and license. Record existing identities and immutable releases.

Acceptance: migration matrix, dependency inventory and working pinned template baseline.

### P1: Registration and release contracts

Define versioned schemas for products, host targets and publisher manifests. Preserve package IDs and releases. Extend current issue approval work rather than replacing it. Central registration changes concern stable identity/trust; routine versions come from publisher releases. Define source-only, prerelease, withdrawal, key rotation and permission expansion handling.

Acceptance: single/multi-host fixtures pass; identity collisions, untrusted key replacement, wrong targets and altered metadata fail.

### P2: Tools and examples

Provide metadata validation and manifest generation from actual artifacts, reusing host packagers. Registry schemas and fixtures stay here; executable example plugins and publisher build workflows belong in independent example repositories. Do not copy runtimes or SDKs into this repository.

Acceptance: one publisher workflow generates valid single/multi-target release metadata with actual hashes and sizes; no invented artifacts or committed secrets; registry CI never executes submitted packages.

### P3: Snapshot and query service

Fetch bounded publisher metadata with validation. Keep marked last-known-good data on temporary failures, but withdrawals override cached entries. Implement host/compatibility filtering, listing, detail and cache behavior. Publish matching pages/API/snapshot versions atomically with rollback.

Acceptance: different host requests return different compatible targets; test pagination, versions, platforms, prereleases, no-match results, cache isolation and failure recovery.

### P4: Website

Build search and host/category filters, cards, product descriptions, screenshots, target versions, compatibility, permissions and documentation/source/download links. Adapt Minted toward Ever Works' layout with full mobile reading support. Sanitize remote content; do not display invented counts or install buttons without verified artifacts.

Acceptance: inspect real registered products and clearly marked multi-host test fixtures; exclude fixtures from production.

### P5: Consumers and migration

Each host sends its identity and available compatibility inputs, resolves the publisher manifest and retains local validation/authorization. Generate any temporary legacy feed from unified data with an explicit retirement condition.

Acceptance: correct host-only results and actual signed-package installation/update tests, preserving installed identities/data. Do not claim multi-host installation acceptance without real packages.

### P6: Deployment

Configure scheduled/registration-triggered builds, Worker assets/API, custom domain and rollback. Validate preview before production. Request missing deployment credentials or domain input only when needed after preparatory work.

Run registry tests, validation, website build, API checks and local Markdown link checks; hosts follow their own repository requirements. Verify domain access, search/details, both host queries, refresh, upstream failure and rollback. Report local code, commits, push, deployment and installation separately.
